【仕様制限】
---------------------------------------------------------------------
  以下は、Professional Edition. リリースモード(*1)における、各項目毎の
仕様を列記したものです。
  全体の仕様は、最初に制限を受けた項目によって変化します。

o １つのメモリブロックの大きさ：2byteから 約16,300byte(*2)
o １つのページ(*3)の大きさ： [ 1,2,4,8,16 ](KByte)のいずれか
o １つのメモリブロックのオーバヘッド：vm_allocの場合 ４byte(*4)
                                      vm_allocFixの場合 ０byte(*4)
o 総メモリブロック数上限：0xffffffff = 4G = 4,294,967,295個
o 総メモリブロック容量上限： 約12,288 × ページサイズ


(*注釈)･･････････････････････････････････････････････････････････････
(*1) デバッグモードでは、各メモリブロックに４byteのチェックコードが
　　 埋めこまれます。
(*2) ページサイズを 16Kbyte にした場合。
(*3) VMM_DosがＯＳ(MS_DOS)にメモリを要求する単位です。
     VMM_Dosは、このページ内に多数のメモリブロックを割り当て、効果的
     に管理します。 [ 動作原理と用語解説 ]をご参照下さい。
(*4) １ページ毎に、12byte消費します。

【関数一覧】
---------------------------------------------------------------------
vm_alloc        メモリブロック（Variable: 可変サイズ）の確保
vm_allocFix     メモリブロック（Fixed: 固定サイズ）の確保
                特定のサイズを頻繁に確保する場合（ほとんどのアプリケー
                ションに該当する）にお使い下さい。
                約５０～９０％の速度向上が期待できます。
vm_check        各種の診断をします
                適当な箇所に挿入すれば、バグの早期発見が可能です。
vm_compaction   vm_freeQuick後のページの一斉圧縮
vm_free         メモリブロックの解放
vm_freeAll      メモリブロックの一斉解放
vm_freeQuick    メモリブロックの高速解放
                多数のメモリブロックをまとめて高速に解放できます。
vm_init         ＶＭＭの初期化       最初に必ず呼び出して下さい。
vm_load         メモリブロックのロード
                次にどれかのVMM関数を呼び出すまでの間、メモリブロックを
                ヒープメモリ上に固定し、そのアドレスを返します。
vm_lock         メモリブロックのロック
                次にvm_unlockまたはvm_unlockAllを呼び出すまでの間、メモ
                リブロﾂクをヒープﾒﾓﾘ上に固定し、そのアドレスを返します。
vm_realloc      メモリブロックのサイズを変更する
vm_size         メモリブロックのサイズを取得する
vm_term         ＶＭＭの終了         最後に必ず呼び出して下さい。
vm_unlock       メモリブロックのアンロック
vm_unlockAll    メモリブロックの一斉アンロック

【動作原理と用語解説】
---------------------------------------------------------------------
o 標準的なメモリブロックの確保と利用方法
- - - - - - - - - - - - - - - - - - - - -
    char *pz;
    pz = (char *)malloc( 128 );     //[1]メモリブロックの確保(*1) 
    if( !pz ) error();
    strcpy( pz, "CodeTips" );       //[2]メモリブロックへの書き込み
    --- Other Functions ---
    puts( pz );                     //[3]メモリブロックからの読み出し
    free( pz );                     //[4]メモリブロックの解放

（動作原理）
    　各コンパイラにより提供されるヒープメモリ(*1)に、必要なサイズの
    メモリブロックが割り当てられ、そのポインタ(*4)が返される[1]。
      このメモリブロックは、ヒープメモリ上の特定のアドレスに存在する
    ので、ポインタにより直接書き込み[2]や読み出し[3]が可能です。
（長所）
    直接ポインタ参照できるので簡単かつ高速である。
（短所）
    ヒープメモリ容量には制限がある。（大抵は、わずか６４０Ｋﾊﾞｲﾄ未満）


o ＶＭＭ＿Ｄｏｓによるメモリブロックの確保と利用方法
- - - - - - - - - - - - - - - - - - - - - - - - - - -
    char *pz;
    VMHAND vh;                         //[a]ＶＭＭハンドル宣言
    vm_init( 0, 0, VM_ALL, 2 );        //[b]ＶＭＭ初期化 
    vh = vm_alloc( 128 );              //[1]ﾒﾓﾘブロックの確保
    pz = (char *)vm_load(vh,VM_DIRTY); //[c]ﾒﾓﾘブロックのロード
    strcpy( pz, "CodeTips" );          //[2]ﾒﾓﾘブロックへの書き込み
    --- Other Functions ---
    --- Other vm_Functions ---
    pz = (char *)vm_load(vh,VM_CLEAN); //[d]ﾒﾓﾘブロックのロード 
    puts( pz );                        //[3]ﾒﾓﾘブロックからの読み出し
    vm_free( vh );                     //[4]ﾒﾓﾘブロックの解放 
    vm_term();                         //[e]ＶＭＭの終了

    +--------------------------+
    |       ヒープメモリ       |
    |                          |    [IN]
    |   +----------+           | ←←←←←／ ページ移動
    |   | ページ   |           |           ↓
    |   |          |           |           ↓[OUT]
    |   |  +---+   |           |           ↓
    |   |  |[B]|   |           |    +--------------------------+
    |   |  +---+   |           |    |        補助メモリ        |
    |   +----------+           |    |    ( XMS, EMS, DISK )    |
    |        +----------+      |    |   +----------+           |
    |        | ページ   |      |    |   | ページ   |           |
    |        |          |      |    |   |          |-+         |
    |        |          |      |    |   |          | |         |
    |        |          |      |    |   |          | |-+       |
    |        |          |      |    |   |          | | |       |
    |        +----------+      |    |   +----------+ | |       |
    +--------------------------+    |     |          | |       |
                                    |     +----------+ |       |
                                    |       |          |       |
                                    |       +----------+       |
                                    +--------------------------+
（動作原理）
    　各コンパイラにより提供されるヒープメモリ(*1)に、指定された固定
    サイズのページ(*2)が割り当てられます。さらに、このページ内に必要
    なサイズのメモリブロック[B]が割り当てられます。
      割り当てられた結果は、ハンドルと呼ぶ32bit値として返されます[1]。
    　このハンドルは、メモリブロックの在処を記録したＶＭＭ独自の値を
    保持しています。
    　ＶＭＭは、適時メモリ移動動作を行い使用頻度の高いページだけをヒー
    プメモリに残し、あとは補助メモリに退避させます。これにより、ページ
    とその中にあるメモリブロックのポインタ(*4)は不定となります。
    　メモリブロックが必要となったとき、ハンドルを手掛かりにＶＭＭは、
    ページを探し出し、ヒープメモリ上に配置し、そのアドレスを返します[c]。
    　メモリブロックは、ロック(*3)されない限り、ＶＭＭ関数の呼び出しの
    度にメモリ移動動作により移動される可能性があります。
（長所）
    ヒープメモリ容量の制限に関らず、実質無限大(*5)のﾒﾓﾘブロックが扱える
（短所）
    ハンドルからポインタ(*4)を得るためのオーバーヘッド(*6)が生じる


(*注釈)･･････････････････････････････････････････････････････････････
(*1) 各コンパイラのマニュアルを御参照下さい。
(*2) ＶＭＭは、ページを最少単位として、補助メモリへの移動を行います。
     ページサイズは、ＶＭＭの初期化時に指定することができます。
(*3) 具体的には、vm_lock によりロック指示する。
(*4) 各コンパイラにより提供される、ポインタ変数により直接参照可能な
     物理アドレス。
(*5) 比較的小さなメモリブロック（4Kbyte未満）を、0xffffffff個未満まで。
(*6) これをより小さくしたのが、ＶＭＭ＿Ｄｏｓです。

【コンパイルとリンクの方法】
---------------------------------------------------------------------
# デバッグ・モード
- - - - - - - - - -
　開発段階に利用するモードです。
  各種のチェック機能が埋めこまれ、バグを感知したときに警告を発します。

（チェック機能概要）

o オーバーライト・チェック
　  メモリブロックへのオーバーライト（不正な書き込み）を適時チェックし
　ます。
　  また、vm_check()により、任意の箇所でチェックさせることもできます。
　  たとえば、全てのオーバーライトの可能性がある行の直後に vm_check()
　を挿入すれば、早期に発見することができます。
　　Ｃのポインタは、Ｃ言語の特徴であり大変な効果をもたらしてくれるので
　すが、オーバーライトに起因するバグの発生率を高めています。このような
　バグは、時間差発生するために発見が困難です。
  　オーバーライト・チェックは、このような問題を解決します。

o メモリリーク・チェック
    vm_term()により、メモリブロックのリーク（解放忘れ）をチェックします。
　  また、vm_check(2)により、任意の箇所でチェックさせることもできます。
  　ＤＯＳプログラムは、シングルプロセスを前提に開発されているために、
  マルチプロセスにおけるリソースの概念が欠けています。
  　メモリブロックは、貴重なリソースです。使い終われば確実に返却するこ
  とを心掛けてください。そうすれば、思いがけないバグの発生を防ぐことに
  もなります。
  　ＶＭＭは、どのような状態であっても vm_term()によりすべてのメモリブ
  ロックを確実に解放してくれます。しかし、メモリリーク・チェックにより
  完成度の高いプログラムに仕上げて下さい。

o メモリロッキング・チェック
    vm_term()により、メモリブロックのロッキング（アンロック忘れ）を
  チェックします。
　  また、vm_check()により、任意の箇所でチェックさせることもできます。
　　メモリブロックをロックすることにより、ページがヒープメモリ上に固定
　されます。これにより、移動可能なページ数が減少すると同時に、ＶＭＭの
　効率も低下します。同時のロック数が増えれば、ヒープメモリの空き容量に
　よっては、移動可能なページがなくなり、「Out of memory」エラーにより
　ＶＭＭは停止します。
　　vm_lock()とvm_unlock()は、１対１に対応していなければなりません。
　vm_unlock()を忘れて vm_lock()を続けると上記のようなロッキング状態に
　陥ります。
    アルゴリズムの検討により、同時期にロックするメモリブロックは２個で
  十分ではないでしょうか（証明した訳ではないが）。
    同時に２つ以上のメモリブロックを利用する場合にだけ、vm_lock()をご利
  用下さい、それ以外は vm_load()を利用して下さい。貴方を、アンロックの
  煩わしさから解放します。

o ＶＭＭセルフ・チェック
　　ＶＭＭ自身が利用しているメモリ周辺をチェックします。
　　また、ＶＭＭ関数の引数や内部処理のチェックを厳密に行うことによりア
　プリケーションからの不正な利用を早期に発見します。

（コンパイル方法）
　ＶＭＭ関数を利用したソースファイルを、/D_AP_DEBUG オプションを付けて、
コンパイルして下さい。
  (例) Compactモデルの場合
       MSC: cl /c /AC /W3 /Ze /D_DOS /D_AP_DEBUG  xxx.c
        BC: bcc -c -mc -K -d -w-eff -a -D_AP_DEBUG  xxx.c

（リンク方法）
　コンパイラとモデルに対応したライブラリをリンクして下さい。
  (例) Freeware Edition. Compactモデルの場合
       MSC: link /noi/e/st:2048 xxx.obj,,nul, Ca_vmm.lib ;
        BC: tlink /c /d c0C xxx.obj,,nul, vmm_Ca.lib emu mathC cC


# リリース・モード
- - - - - - - - - -
  デバック・モードで埋めこまれる機能を除き、最高のパフォーマンスを提供
するモードです。
　ソースリストの変更は、一切不要です。

（コンパイル方法）
　ＶＭＭ関数を利用したソースファイルを、/D_AP_DEBUG オプションを外して、
コンパイルして下さい。
  （assert()を利用している場合は、/DNDEBUG オプションを付けます。）
  (例) Compactモデルの場合
       MSC: cl /c /AC /W3 /Ze /D_DOS /DNDEBUG  xxx.c
        BC: bcc -c -mc -K -d -w-eff -a -DNDEBUG  xxx.c

（リンク方法）
  デバック・モードと同様に、コンパイラとモデルに対応したライブラリを
リンクして下さい。
  (例) Freeware Edition. Compactモデルの場合
       MSC: link /noi/e/st:2048 xxx.obj,,nul, Ca_vmm.lib ;
        BC: tlink /c /d c0C xxx.obj,,nul, vmm_Ca.lib emu mathC cC
